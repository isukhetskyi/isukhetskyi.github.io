Part One

The Setup

Everything the agent knows lives in files - not in my head, not in the chat

Core idea for part 1: if the agent has to be told something twice, it belongs in a file. Everything on the next slides is just files in the repo - versioned, reviewable, and shared across tools.

The Pet Project: BioMetric

  • A sovereign health analytics platform - biomarker trends, automated lab-report (PDF) ingestion, medication inventory & budget forecasting
  • .NET 10 Web API + Blazor WebAssembly client with MudBlazor 9 + Cosmos DB (in-memory fallback)
  • Vertical-slice features, multi-tenant by design (ITenantRepository<T>)
  • Built with an agent in the loop - so the setup has to carry real weight

Four Layers of Agent Context

1 - Rules  AGENTS.md · GEMINI.md · .agents/rules/*.md
How we write code here: architecture, C# idioms, Blazor, testing
2 - Domain memory  CONTEXT.md · docs/adr/ · docs/kb/ (incl. plans/) · docs/wbs/
What the system means and why it is built this way
3 - Skills  .agents/skills/<name>/SKILL.md
Reusable procedures the agent runs on demand (/grilling, /plan-feature, /implement-feature, /review-changes ...)
4 - Guardrails  hooks.json · autonomy policy · dotnet build/format/test gate · CI
What the agent may do - and what must pass before a commit
Rules say how · Domain memory says what & why · Skills say in what order · Guardrails say how far
This is the mental model for the whole talk. Most people stop at layer 1 (a rules file). The jump in quality came from adding layer 2 (so the agent uses my vocabulary and respects past decisions) and layer 3 (so multi-step work is repeatable instead of re-prompted).

Layer 1 - Rules That Encode Our Decisions

dotnet-development.md

  • Layering: Shared stays UI/ASP.NET-free
  • Controllers inject ITenantRepository<T> - never ICosmosRepository<T>
  • No .Result / .Wait(), always CancellationToken
  • Blazor: no [Parameter] mutation, @key in loops, dispose subscriptions
  • Cosmos LINQ: no .CountBy() in queries - materialize first

testing.md

  • Method_State_ExpectedResult naming + AAA
  • Fakes over mocks: InMemoryRepository<T> + MockCurrentUserService
  • Every controller gets a cross-user isolation test
  • Async tests return Task, never async void
Clean commit gate: dotnet build --no-incremental (0 warnings) → dotnet format --verify-no-changes → dotnet test
Good rules are specific and falsifiable - "use ITenantRepository" beats "follow good architecture".
Rules are scoped by file glob: dotnet-development.md for *.cs / *.razor / *.csproj ..., testing.md for tests/**/*.cs - loaded only when relevant files are in play.
Every one of these rules exists because the agent (or I) got it wrong once. The tenant-repository rule is the most valuable: it turns a security property - no cross-user data leaks - into a mechanical check that a reviewer, or a skill, can verify from the diff. The anti-pattern examples in the rules files (BAD / GOOD blocks) help a lot more than prose.

Layer 2 - Domain Memory

  • CONTEXT.md - a glossary only: canonical terms and the words to avoid
  • docs/adr/ - decisions that are hard to reverse, surprising, and a real trade-off
  • docs/kb/ + docs/wbs/ - feature specs (F-xxx), acceptance criteria, business rules, risks
  • docs/kb/plans/F-xxx-plan.md - the approved implementation plan, written by plan-feature
  • docs/traceability.json - links features ↔ entities ↔ rules
Skills read this before exploring code - so output uses my vocabulary and flags ADR conflicts.

The _Avoid_ lines are the trick: they stop the agent drifting into synonyms, which keeps code, tests, issues and docs in one vocabulary. Low-Stock Alert is the glossary term F-067 builds on - the feature changes when that alert is delivered, not what it is. ADR-0018 (F-067) references ADR-0016 and ADR-0008 as context - a good example of the agent being told about past decisions instead of re-litigating them. The domain-modeling skill only offers an ADR when all three conditions hold (hard to reverse, surprising, real trade-off), which keeps the ADR folder small and meaningful.

Curated, not collected: a small set of focused skills - four of them custom to this repo.
Every skill's name + description sits in the agent's context all the time - each extra skill is a recurring token cost and a chance to pick the wrong one.
Don't read the table. Three takeaways: (1) skills cover the whole lifecycle, not only coding; (2) the four orange ones - plan-feature, implement-feature, review-changes, generate-commit-message - are specific to this repo: they reference F-xxx feature IDs, the KB and AGENTS.md checklists; (3) I keep the set small on purpose: fewer, sharper skills means the agent chooses correctly more often and less context is burned on descriptions. Every skill has a third-person "Use when..." description and an allowed-tools fence.

Anatomy of a Skill

review-changes/
├─ SKILL.md              ← the procedure (short)
├─ references/
│  ├─ review-checklist.md  ← C#, Blazor, tests
│  └─ code-smells.md       ← Fowler baseline
└─ scripts/
   └─ verify-gate.ps1      ← build+format+test

# SKILL.md frontmatter
---
name: review-changes
description: Reviews uncommitted git
  changes against AGENTS.md ... Use when
  the user asks to review changes ...
allowed-tools: Bash(powershell *),
  Bash(git status *), Bash(git diff *),
  Read, Grep, Glob
---
  • A skill is a folder with a SKILL.md - frontmatter + instructions
  • description ("Use when...") is what makes the agent pick it
  • allowed-tools fences what it can run - review is read-only git + one script
  • disable-model-invocation → only runs when I call it (used by generate-commit-message, to-spec, triage ...)
  • 3 levels: metadata always loaded → SKILL.md on invoke → references/ and scripts/ only when needed
  • Deterministic work goes in a script; the agent reads a 10-line summary, not 500 lines of build log
Rules load when matching files are touched. Skills are loaded on demand, in layers - a long checklist costs nothing until a review actually needs it.
Take review-changes as the example: SKILL.md is just the procedure, the checklist and the Fowler code-smell baseline live in references/ (read on demand), and the build/format/test run lives in verify-gate.ps1 which prints a short markdown summary - far cheaper for the agent's context than raw dotnet output. allowed-tools pre-approves exactly what the skill needs (powershell script, git status/diff) and nothing else. Note disable-model-invocation: the agent will not decide on its own to draft a commit message or publish tickets - only I trigger those.

Layer 4 - Guardrails

Command allowlist hook

  • hooks.json → PreToolUse on shell commands → command-filter.ps1
  • allow: dotnet build|test|restore, git status|diff|log
  • ask: everything else

Autonomy policy AGENTS.md §7

  • Free: build, test, read, edit in src/ tests/ .agents/
  • Confirm: reset --hard, push --force, cloud provisioning
  • Never leave the workspace root

Per-skill tool fences

  • allowed-tools in every SKILL.md - e.g. commit skill: git status|diff + Read only

Quality gates

  • TreatWarningsAsErrors + analyzers (Sonar, Meziantou, Roslynator)
  • .editorconfig enforced via dotnet format
  • verify-gate.ps1: build + format + test in one command, short summary out
  • CI: build-and-test.yml on push / PR to main
  • Build and review skills end with a verification stage - not "looks good"
Safe, boring commands run without prompts → I only get interrupted for decisions that matter.
The hook is deliberately tiny: a regex allowlist. Anything not matched returns "ask", so the failure mode is "I get a prompt", never "something ran silently". Autonomy is the productivity lever - without it the agent asks permission 40 times per feature and you stop paying attention to the prompts that matter.

Humans own the decisions (steps 1, 2, 5). The agent owns the execution (3, 4) - and each step's output is the next step's input.
The important design choice is where the human sits. Steps 1 and 2 are cheap to change - this is where I spend my attention. Once the plan file is approved, implementation is mostly mechanical because the rules, the spec and the plan already constrain it - the plan is the hand-off contract between steps 2 and 3.

1Research the Task - grilling + domain-modeling

grilling - the interview

  • Maps the task as a design tree; asks the whole "frontier" per round, each question with a recommended answer
  • Facts (code, files) it looks up itself via read-only tools - decisions it asks me
  • Doesn't act until I confirm we share an understanding

domain-modeling - the docs

  • Challenges fuzzy terms against the CONTEXT.md glossary; stress-tests with edge-case scenarios
  • Writes glossary terms inline as they crystallise; offers an ADR only if it's hard to reverse, surprising, and a real trade-off
  • Cross-checks my claims against the code
I invoke /grilling; the docs skill does its part whenever terms or decisions come up. 
// illustrative round - based on the F-067 reminder-time decision (ADR-0018)
❓ Q1 - Delivery model: The worker sleeps 24h and fires at 10:00. If the machine is off
   at that moment, the alert is lost for the day. Keep a single timer, or tick periodically?
➡️ Periodic 15-minute aligned ticks with same-day catch-up - a 09:00 alert still fires at 11:30.

❓ Q2 - Time zone: Per-user time zones, or one anchor for everyone?
➡️ Anchor to Europe/Kyiv (matches our lab / pharmacy ecosystem); revisit if users go abroad.

❓ Q3 - Existing profiles: Stored preferences have no reminder time yet. Migrate them?
➡️ No migration - null/empty evaluates as "10:00", so F-065 behaviour is unchanged.
Two skills work together here: the interview is /grilling and the glossary/ADR discipline lives in domain-modeling. The grilling skill is restricted to Read, Grep and Glob - it can investigate but cannot edit anything; the writing of CONTEXT.md and ADRs belongs to domain-modeling, which has Write/Edit. Show the real skill text if asked: "Interview the user relentlessly until you reach a shared understanding... The session is done when the frontier is empty." The big win is that it doesn't act until I confirm we're aligned. The Q&A above is illustrative of the style (I'm not quoting a transcript), but the decisions are the real ones recorded in ADR-0018 for F-067: periodic 15-minute ticks with same-day catch-up, Europe/Kyiv anchor, and a "10:00" default for backward compatibility.

New step in the loop: planning is its own custom skill. The key change in this step: implement-feature no longer re-derives requirements from scratch when a plan exists - the approved plan is the blueprint, and the skill only falls back to discovering the spec from the KB and WBS when there is no plan. It executes the plan's phased checklist and ticks tasks as it goes, which makes progress visible and interruptions cheap. The skill links to dotnet-development.md and testing.md via relative links, so rules stay in one file. Stage 5 also updates docs/kb/features/index.md and FEATURE_PRIORITIES.md - the spec registry is kept honest by the same workflow that writes the code.

4Review - review-changes custom

What it does

  1. git status + staged/unstaged diff + untracked files
  2. Runs one script: verify-gate.ps1 → build (0 warnings), dotnet format, dotnet test → short summary
  3. Reads references/review-checklist.md: C#, Cosmos, Blazor lifecycle & leaks, MudBlazor, tests
  4. Reads references/code-smells.md (Fowler baseline) and, if there's an originating issue/spec, checks for missing requirements and scope creep
  5. Structured report
## Code Review Report
Build: Passed  Tests: N/N passed

#### 🚨 Blockers
- File:Line - violates AGENTS.md §3.1
#### ⚠️ Recommendations
- File:Line - use collection expr.
#### ✅ Compliant Highlights
- clean disposal, @key on lists

Verdict: CHANGES REQUESTED
One review skill, two lenses: Standards (checklist + smells) and Spec (does it do what the issue asked?).
The sample report is a format illustration, not real output. review-changes is the single review skill: it is tied to AGENTS.md and covers two lenses - standards (checklist plus the Fowler smell baseline) and spec (only when an originating issue or spec exists). The checklist and the smells live in references/ so they are read only when a review actually runs, and the build/format/test step is a script that returns a short summary. For F-067 this is exactly what runs after implementation: the plan's acceptance criteria are the spec lens, AGENTS.md and the rules are the standards lens.

5Commit - generate-commit-message custom

  • Reads staged + unstaged changes, prefers the staged set if both exist
  • Conventional Commits: type(scope): imperative subject + bullet body + footers
  • Gives a copy-paste command - I run the commit myself
  • Explicit-only (disable-model-invocation) and read-only: allowed-tools = git status, git diff, Read

How to Start on Your Own Project

  1. Write a short AGENTS.md: stack, build/test commands, 5-10 rules the agent keeps breaking
  2. Add a CONTEXT.md glossary the first time you catch the agent using the wrong word
  3. Record an ADR only for decisions that are hard to reverse and surprising
  4. Turn your most repeated multi-step prompt into a SKILL.md
  5. Add an allowlist for the safe commands so you stop clicking "approve"
  6. Run the loop: grill → plan → implement → review → commit - and fix the setup when it hurts
